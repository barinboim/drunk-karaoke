# Пьяное караоке · Drunk Karaoke — памятка для агентов

Локальная караоке-игра. Мелодия и ритм настоящей песни остаются нетронутыми, а слова
заменяются **целыми записями** из постороннего датасета: названиями товаров, побочными
эффектами из инструкции к лекарству, объявлениями с доски. Человек поёт их под знакомую
мелодию — в этом вся шутка.

Всё работает локально: ни LLM, ни нейросетей, ни API-ключей, ни запросов наружу.
Подбор текста — детерминированный JavaScript в браузере.

## Запуск и проверка

```sh
npm run library                      # индексировать папки с песнями UltraStar
npm run backdrops                    # скачать фоны с Викисклада (один раз)
npm start                            # http://127.0.0.1:4173/
npm test                             # 13 тестов движка и разбора разметки
npm run corpora                      # проверить все датасеты
```

**Перед коммитом любых правок движка гоняй `npm test`.** Тесты сторожат инварианты,
которые легко сломать незаметно.

## Нерушимые правила

Их нарушение убивает игру, даже если код формально работает.

1. **Запись неделима.** Единица подстановки — целая строка датасета. Её нельзя резать,
   переставлять внутри, дополнять словами или склеивать из кусков. Любой обрывок посреди
   мысли — это провал.
2. **Слогов ровно по нотам.** Строка песни из 14 нот получает ровно 14 слогов. Это жёсткое
   условие, а не пожелание.
3. **Ничего не выдумывается.** Каждое слово дословно из датасета, с точными координатами.
4. **Повторяющиеся строки песни получают один и тот же текст.** Припев остаётся припевом.
5. **Ударения — судья, а не генератор.** Они выбирают между валидными вариантами, но никогда
   не разрешают нарушить правила 1–3.
6. **Никаких сетевых запросов в рантайме игры.** Сеть используют только скрипты сборки.

## Как собирается строка

1. Датасет режется на записи: файл-список — одна запись на строку, разделы через `## Заголовок`.
   Проза (свой .txt со сплошным текстом) режется по знакам препинания на законченные клаузы.
2. Для каждой длины строки песни движок **сэмплирует комбинации** из 1–4 целых записей, сумма
   слогов которых точно равна числу нот. Таблица достижимости `feasible[k][rest]` гарантирует,
   что выборка никогда не заходит в тупик.
3. Комбинации оцениваются и лучшие идут в beam search по всей песне (рифма с одной из четырёх
   предыдущих строк, неповторное использование записей).
4. **Долгая нота — на конце слова.** В оригинальных песнях так в 89% случаев: композитор
   тянет гласную там, где слово кончается. Тянуть середину слова невозможно — «ле———тнее»
   не спеть. Штраф пропорционален длине ноты, поэтому на песнях без долгих нот он не стоит
   ничего. Без правила у нас было 50% попаданий, с ним — 77–92%.
5. **Протяжные ноты.** Нота длиннее `LONG_NOTE` (0.9 с) — это место, где вокал тянут на одной
   гласной. Движок сравнивает саму гласную (я→[а], ё→[о], е→[э], ю→[у]) и проверяет, можно ли
   слог вообще протянуть: «крем-брюле» тянется, «кинетический песок» — нет. На реальной песне
   совпадение гласной выросло с 3% (случайность) до ~52%.

### Оценка комбинации

```
−3.5 × расхождение ударений
+1.6 × доля протяжных нот с совпавшей гласной
−0.9 × доля протяжных нот на непротяжном слоге
+0.55 × рифма            −0.9 × то же последнее слово
−0.7 × доля неизвестных ударений
−1.8 × повторное использование записей
−0.7 × одинаковое первое слово у соседей   («Пицца … · Пицца …»)
−0.3 × соседи из одного раздела
+0.25 × записи оказались соседями в файле
−0.35 × каждый лишний кусок сверх одного
```

Веса подобраны замерами, а не на глаз. Если меняешь их — замеряй заново: расхождение
ударений, долю совпавших гласных на длинных нотах, число разных версий на 40 seed.

## Что уже пробовали и отвергли

Каждый пункт — замеренная неудача. Не повторяй их.

**Строка из подряд идущих записей.** Первая версия брала записи только соседними: казалось,
что так текст будет связнее. На деле это сжимало выбор до ~5 комбинаций нужной длины, и движку
приходилось брать что дают — отсюда кривые ударения («Плов узбе́кский с бара́ниной» вместо
«бара́ниной») и однообразие внутри строки («Пицца … · Пицца …»). Свободная сборка из любых мест
корпуса подняла пул на порядок: расхождение ударений упало с 4–5% до 0.3%. Записи при этом
по-прежнему **целые** — резать их нельзя никогда.

**Перестановка разделов на каждый seed.** Попытка добавить разнообразия: свой порядок разделов
для каждой версии. Разнообразие выросло, но связность рухнула до 16%, а расхождение ударений
до 8%. Откатили к простому: одна случайная точка входа в корпус на версию.

**Разрыв строки по любой длинной паузе.** Пауза ≥0.8 с сама по себе даёт 253 разрыва на 6766
строк — разметка рассыпается. Работает только связка «долгий распев **и** пауза».

**Штраф за разрыв слова без учёта длины ноты.** Постоянный штраф портил ударения на песнях,
где долгих нот почти нет, то есть брал плату там, где пользы ноль. Штраф, пропорциональный
длительности ноты, на таких песнях стоит ровно ничего.

**Датасет из коротких названий.** Медиана 6 слогов и ноль записей на 14 означают, что строка
песни в 14 слогов физически не может быть одной фразой. Никакая остроумная тема этого не лечит —
лечит только распределение длин. Сравнение на одной и той же песне: отзывы (медиана 11) дают
88% цельных строк, меню (медиана 6) — 3%.

## Как проверять изменения

Любая правка подбора меряется по одному набору. Все числа — на «Батарейке» и «На Заре»,
12 сидов, если не сказано иное.

| метрика | что значит | ориентир |
|---|---|---|
| расхождение ударений | `100 − fit`, усреднённое по строкам | ≤3% на лёгкой песне |
| цельных строк | доля строк из одной записи | чем больше, тем связнее |
| гласная на распеве | совпадение на нотах >1.2 с | 85%+ |
| долгая нота на конце слова | в оригиналах 89% | 80%+ |
| соседи из одного раздела | однообразие внутри строки | <10% |
| разных версий | на 12–40 сидов | почти все |

Правило: **сначала замер, потом правка.** В этом проекте «очевидная» причина дважды оказывалась
неверной — рваность списывали на темы датасетов, а дело было в длинах; потерю ударений
списывали на словарь, а дело было в хвостовых пробелах разметки.

## Ловушки разработки

- **Точечная замена строки молча не срабатывает,** если строка отличается хоть на символ. За
  сессию так трижды: токенизатор остался кириллическим, из воркера пропал целый блок загрузки
  словарей, подпись под сценой не поменялась. Симптом — «правка не подействовала», а ошибки нет.
  Проверяй результат замены, а не факт её запуска.
- **Пороги в тестах, взятые от настоящей песни, ломаются на синтетической фикстуре.** В фикстуре
  из 15 нот одна строка — это треть песни, поэтому «охват <20%» там недостижим. Калибруй пороги
  на том, на чём тест реально работает.
- **Плейлист-фикстуру легко принять за реальные данные.** Сверяй числа перед тем, как называть
  их в отчёте: «строк стало 21 вместо 41» оказалось сравнением с другой песней.

## Разбор UltraStar: чего не ломать

Парсер чинит реальные файлы, а не требует идеальных. Каждая мера появилась из-за конкретной
поломки на коллекции из 169 папок:

- **Граница фразы бывает и без знаков — чисто музыкальная.** Долгий распев, а за ним тишина:
  так устроен зачин «На заре», где нота держится 4.25 с и после неё 1.4 с молчания, а знаков
  препинания нет вовсе. Пороги подобраны замером: связка «распев ≥1.5 с плюс пауза ≥0.5 с»
  даёт 27 разрывов на 6766 строк, тогда как одна только пауза ≥0.8 с разносит разметку
  на 253 куска. После разделения совпадение гласной на распеве выросло с 63% до 88%.
- **Сильная пунктуация внутри строки — граница фразы.** Разметка нередко сваливает несколько
  музыкальных фраз в одну строку, и короткое восклицание тонет в стене текста. Если нота
  кончается на `!`, `?`, `…` или `.` и после неё пауза от 0.25 с, строка делится. На всей
  коллекции это затрагивает 31 строку из 6766 — приём хирургический, русские песни не рассыпаются.
- **Хвостовые пробелы значимы.** Часть чартов помечает границу слова пробелом в конце слога,
  а не в начале. Нельзя делать `trimEnd()` на строке нот — это склеивает всю строку в одно
  слово и теряет все ударения в ней. Эта ошибка стоила 53% всех пропущенных ударений.
- Ноты с несколькими гласными делятся на слоги с пропорциональным таймингом.
- Ноты без гласных приклеиваются к соседнему слогу.
- Дуэты `P1`/`P2` сводятся в одну дорожку, дубли партий отбрасываются.
- Латинские двойники кириллицы внутри русских слов чинятся.

**Английская разметка читается.** Ноты в ней НЕ дробятся по гласным буквам: в английском
написание о слогах не говорит («through» — одна нота и три гласные буквы). Язык определяется
по тому, чего в тексте нот больше, и попадает в `song.language`.

Итог: 169 папок из 169.

## Библиотека песен

`scripts/library.mjs` обходит папки с разметкой. Что выяснилось на коллекции из 169 папок:

- **Битые mp3.** Девять файлов из 345 начинаются с мегабайтов нулей: `ffmpeg` их вытягивает
  сканированием, а браузер отказывается играть вовсе («no supported sources»). Индекс проверяет,
  что декодер может начать с байта ноль — тег `ID3` или синхрослово MPEG, — и берёт из папки
  другую дорожку. Одну песню пришлось исключить: там обе дорожки битые.
- **Одна песня в нескольких папках.** Схлопываются по паре «исполнитель + название», выживает
  копия с минусовкой.
- **Варианты в заголовках.** `#TITLE` часто несёт «(Минус+Бэк)», «Дуэт» и прочее. Чистится
  регулярками, но помни: `\b` в JavaScript работает только с латиницей, для кириллицы нужны
  явные разделители.
- **Обложка против фона.** `#COVER` — обложка, `#BACKGROUND` — кадр из видео с выжженным текстом.
  Берём первое, иначе в плитках оказываются кадры чужого караоке.
- **Нумерация корней.** В ссылку `library/<N>/…` идёт индекс среди **внешних** корней, а не среди
  всех: сервер читает только внешние. Считать по всему списку — значит разъехаться на единицу
  и получить 404 на всех обложках.

## Публикация

Сайт собирается GitHub Actions из ветки `main`, песни лежат в отдельной ветке `songs` и
подмешиваются при сборке. Так сделано потому, что `git subtree push` перезаписывает ветку
целиком и снёс бы загруженные вручную песни. Локально `dist/songs/` в `.gitignore` — этой папки
для разработки как бы нет.

**Что не публикуется никогда:** фонограммы, тексты песен, референсные кадры чужого караоке.
Публикуются только приложение, датасеты и фоны с Викисклада (с указанием авторов в `credits.html`).

## Два языка

Движок работает и с русскими, и с английскими песнями, причём корпус может быть на другом
языке, чем песня: слоги и векторы ударений сопоставимы, а гласные для протяжных нот приведены
к общим классам (`а о э и у`), так что английское `AY` совпадёт с русским «а».

| | русский | английский |
|---|---|---|
| слоги | число гласных букв | число гласных фонем из CMUdict |
| ударение | `accents.txt` поверх OpenRussian | цифры `0/1/2` в CMUdict |
| деление написания | после каждой гласной | межслоговое правило: одну согласную отдаём правому слогу, из двух и более одну оставляем левому |
| рифма | хвост от ударной гласной | фонемы от главноударной до конца |

Английское слово вне CMUdict получает слоги по группам гласных и нейтральное ударение — как
и русское слово вне словаря. По «Boulevard of Broken Dreams» без ударения остаётся 1.8% слогов.

`npm run cmudict` качает CMUdict и кладёт `dist/data/cmudict.json` (3.6 МБ, 125 тысяч слов).
Воркер тянет его лениво — только если песня или корпус английские.

## Словарь ударений: один на всех

`dist/data/dictionary.json` — словоформы OpenRussian (558 тысяч, CC BY-SA 4.0).
`dist/data/accents.txt` — **наше дополнение, и оно центральное.** Туда стекается всё, что
OpenRussian не знает: местоимения (их склонения там просто нет), заимствования, современные слова.

Датасет может нести раздел `## ~ударения` — это удобство для того, кто присылает файл со стороны
и не может править общий словарь. Но это временное хранилище: `npm run accents -- --apply`
переносит находки в `accents.txt` и вычищает разделы из датасетов.

**Почему так.** Сначала ударения жили внутри каждого датасета, и это оказалось ошибкой:
к двенадцатому датасету накопилось 924 записи, из которых 66 слов были выведены по два-три раза
разными составителями. Тринадцатый вывел бы их в четвёртый раз. При слиянии нашлось пять мест,
где датасеты разошлись в ударении одного слова, — все пять оказались ошибками, а не разными
мнениями, и приведены к норме списком `RESOLVED` в `scripts/accents.mjs`.

Вывод: словарь один, находки общие. Составитель корпуса должен выводить ударение только для слов,
которых в проекте ещё не было.

### Старое описание

`dist/data/dictionary.json` — словоформы OpenRussian (CC BY-SA 4.0).
`dist/data/accents.txt` — **наше дополнение, которое важнее словаря.** Туда идёт всё, чего
OpenRussian не знает или знает неверно. Важно: в OpenRussian нет склонения местоимений, поэтому
«тобой», «нами», «него» без дополнения остаются без ударения.

Формат: одна словоформа в строке, знак ударения `U+0301` после гласной, `#` — комментарий.

## Оценка пения

Высота берётся из самой разметки: у каждой ноты есть `pitch`, и во всех 168 песнях коллекции
это настоящая мелодия, а не заглушка. Признак золотой ноты (`*`) тоже сохраняется и весит вдвое.

`dist/pitch.js` — автокорреляция с нормировкой по накопленному среднему (приём из YIN). Две
вещи, на которых легко ошибиться и которые уже стоили точности:

1. **Разностную функцию надо делить на число слагаемых.** Без этого сумма падает с ростом
   сдвига и найденный период систематически короче настоящего.
2. **Порог пересекается на входе в провал, а период соответствует его дну.** Если остановиться
   на входе, ошибка достигает 90 центов на низком голосе — почти полутон. Нужно спускаться
   до дна. После обеих правок погрешность на контрольных тонах — меньше цента.

Сравнение идёт **по кругу из двенадцати полутонов**: октава не важна, иначе мужчина и женщина
не смогли бы петь одну песню. Это проверено тестом.

Дубль реплики знает свою строку (`take.line`): музыка подводит к ней три секунды и захватывает
хвост предыдущей, но оценивать надо только ту, которую просили спеть.

Оценка считается в отдельном воркере: на целой песне это сотни миллионов операций.

## Экспорт

Звук сводится офлайн (`mixSong`), **громкость минусовки в транспорте — она же мастер сведения**:
насколько приглушил музыку при пении, настолько она приглушена в файле.

Ролик пишется **в реальном времени** — иначе браузер не отдаст видеодорожку: кадры рисуются на
canvas по часам того же `AudioContext`, из которого играет сведённый буфер, поэтому картинка не
уезжает от музыки. `canvas.captureStream` + дорожка из `MediaStreamAudioDestinationNode` идут в
`MediaRecorder`. Формат выбирается по `MediaRecorder.isTypeSupported`: MP4 (H.264+AAC), иначе WebM.

При правке рендера помни: разделитель `·` между записями в canvas надо рисовать руками — в DOM
это `::before`, и без него строка склеивается в один неразрывный кусок и вылезает за кадр.

### Кадр ролика

**Сейф-зоны лент — не украшение, а условие.** В Reels верх кадра закрывает интерфейс, низ —
подпись и имя автора, правый край — столбец кнопок. Для 1080×1920 это 250 сверху, 422 снизу
и по 119 с боков; в `SAFE` они долями, чтобы не зависеть от размера. Боковой отступ одинаковый
с обеих сторон, хотя мешает только правый: асимметричный сдвигает центрованный текст, и это
видно. Вся шапка и вся строка песни живут внутри этих границ.

**Фоны тасуются до того, как список урезан.** Набор с Викисклада лежит по темам, и первые
двадцать четыре файла — это десять павлинов, тринадцать водопадов и один закат. Отсюда бралась
«случайная» последовательность. Тасовать после `slice` бессмысленно: павлины остаются.

**Обрезка идёт по цвету, а не по резкости.** Фоны горизонтальные, ролик вертикальный, и обрезка
по центру режет объект. `focusOf` ищет скользящим окном место с наибольшим весом содержимого,
где вес — насыщенность **выше порога** плюс немного резкости. Порог решает всё: если считать
всякую деталь, листва и гравий берут числом. Замер по 200 фонам, доля объекта, оставшаяся
в вертикальном кадре: обрезка по центру 48%, по резкости 51%, по цвету выше порога **68%**;
на павлинах 62% против 81%. Штраф за шов, проходящий по объекту, пробовали — 67%, то есть ничего.

**Сетка старого экрана — точечная матрица, а не полосы.** Кадр виден сквозь круглые точки
с размытым краем, между точками чуть притемнено; плитка строится один раз и повторяется узором.
Полосы пробовали дважды и оба раза мимо: по три пикселя с шагом шесть — на телефоне ровная серая
пелена вместо полос, а крупные жёсткие полосы вышли слишком тёмными и грубыми. Нынешние числа:
сорок пять точек по высоте кадра, среднее затемнение 10.5% против 16.6% у полос. На читаемость
не влияет — текст рисуется поверх.

**Порядок шапки: логотип, адрес сайта, название песни.** Всё по центру, каждое отдельной
строкой, кегль растёт сверху вниз. Логотип ни к чему не приклеен: адрес был подписью под ним
в углу кадра, и в ленте это читалось как мелкий мусор у края.

## Цельность строки

Строка из одной целой записи всегда лучше склейки из кусков. Это зависит не от темы датасета,
а от **распределения длин**: чтобы закрыть строку в 14 слогов одной фразой, нужны записи ровно
на 14 слогов. В меню их ноль, поэтому там строка всегда собирается из трёх-четырёх кусков.

Выборка сначала пробует закрыть строку одной записью и только потом собирает из нескольких.
После этой правки доля цельных строк выросла с 15% до 74–84% на датасетах с длинными записями
и осталась низкой там, где длинных записей нет. Вывод для авторов датасетов — в `docs/DATASETS.md`.

## Наполнение датасетов

Это основная задача, которую отдают на сторону. **Читай `docs/DATASETS.md`.**

Устройство рассчитано на то, чтобы датасет мог принести человек, ничего не знающий о коде:
папка `dist/corpora/`, один файл — один датасет, внутри шапка с названием и служебный раздел
с ударениями. Регистрировать нигде не нужно. Список датасетов строится сам: локально его на лету
отдаёт `scripts/server.mjs`, на сайте — `scripts/corpora.mjs` в сборке. `dist/corpora/index.json`
производный и в репозиторий не коммитится.

`npm run corpora` проверяет все датасеты и объясняет замечания. Ключевая метрика — доля записей
в 8–16 слогов («в ядре»): ниже 55% датасет звучит рвано независимо от темы.
